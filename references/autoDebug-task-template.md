# autoDebug 任务派发模板（build → autoDebug）

> 使用时机：build 需要**多步真机操作 / 取证 / 复现验证**时，按本模板组织 prompt 派给 autoDebug。
> 单条简单命令（如截图、抓日志、点一个已知元素）**不要派 autoDebug**，build 直接执行即可。

## 为什么要有模板

autoDebug 早期存在「提前返回」：只执行 2~3 步就返回、或因超时中断、或遇错即弃。
主要原因不是模型能力，而是**派发信息不足**：只说「帮我测一下登录」，没给步骤、完成标准、超时要求。
本模板把「做什么 / 做到什么程度 / 做不到怎么办」三件事写全，显著降低提前返回。

## 模板（复制填空）

```
任务目标：<一句话，如「复现登录后崩溃问题」>

操作步骤：
0. 先跑 `bash <S>/scripts/doctor.sh --platform <目标平台>`：rc≠0 ⇒ 按输出登记的阻塞项回报（**不要自行安装/升级依赖**）
1. <步骤描述>（方式：bg.sh 后台 / 前台；预估超时 <N>s）
2. <步骤描述>
3. <步骤描述>

完成标准：<什么现象算成功，精确可判定>
> 优先写成结构化断言（`has` / `has-not` / `count` / `match`），与「完成标准」二选一即可，
>   不要两处各写一套（数字冲突时模型会服从更近的一处）。断言文件示例：
>   ```
>   has 我的设备
>   has-not 加载中
>   count 在线 3
>   ```
> 判据优先用 `assert_page.sh` 拿 rc + 一行结论；需要看全貌用 `snapshot.sh`（≤40 行摘要）。
> ⚠️ 若判据是日志签名，必须先在源码 `grep` 确认该字符串**真实存在**再用；
>   禁止用方法名猜测（`play()` ≠ `play() called`）。签名写错 → 必然空等到超时。

失败处理：
- 若 <关键定位步骤> 找不到目标元素：先 `snapshot.sh` 取摘要（需要全量用 `--json`）定位失败层；仅当 exit 4（语义树为空）才 `shot.sh`，再降级 Maestro / Vision
- 目标需要滚动才可见：用 `android/findtap.sh <关键词>`（自动滚动查找+点击），不要手工「滑一次 dump 一次」；若它首屏即返回 rc=1 且报「语义树无内容」，说明页面无语义树，**不要再滑**，按输出降级 Maestro → Vision → 坐标
- 截图/元素像是过渡态（白屏、半透明、列表抖动）：先 `android/settle.sh` 再取证，避免把动画中间帧当页面错乱；它返回 **rc=3** 表示判定不可信（语义树不可用），不是「已静止」——改用默认 `auto` 或 `--mode screen`
- 若 Maestro 报错：查 build/debug/maestro_output.log，区分「流程失败」与「被强杀（LOST）」
- 某步连续失败 2 次（= 原命令重试 1 次 + 降级 1 次，共 3 次执行）即停止并回报，不要反复重试

超时要求：预估 >60s 的命令用 bg.sh 后台模式；等待时短轮询（wait --timeout 100 循环调用），
          直到拿到退出码 0/1/3 才算结束；日志长时间无新增不等于卡死，勿提前终止。
          等日志签名出现用 `logwatch.sh <签名> <超时>`（动态跟随 PID）；超时须 ≤100，更长等待用 `bg.sh` 包装。
          禁止自己拼 `adb logcat --pid=$PID` 轮询。
          ⚠️ 等待页面就绪**不要写裸 `sleep N`**（不在子代理 shell 白名单，会被秒拒）：
          用 `bash <S>/scripts/android/settle.sh`（等 UI 静止）或 `adb shell sleep N`。
          ⚠️ 目标页面前提（登录页 / 已登录 / 首启协议页）**必须写明是否允许清数据**；
          未写清时子代理可能自行 `adb shell pm clear`，导致复现前提漂移。

回报要求：执行完所有步骤后统一输出，含步骤完成表；命中 autoDebug 的五类中止条件才可提前停止
          每条结论后必须跟证据坐标 `证据: build/debug/<文件>:<关键词/行>`；**不得仅用截图作证据**
          （截图默认只报路径、不 Read；确需 Read 须写明理由）；拿不到证据就写「未验证」，不得写「已修复」
```

## 派发前自检清单

- [ ] **`.debug.env` 是否已就绪**（主 agent/人工在项目根准备好）？autoDebug 档**没有写权限**、**不能自举** ⇒ 缺失时它会直接登记阻塞返回
- [ ] 是否要求先跑 `doctor.sh`（一次自检代替逐项探测），且写明「缺依赖只回报、不自行安装」
- [ ] 若目标工程**不是 Flutter**（无 `pubspec.yaml`）：任务里是否已写明「**跳过 Maestro / Appium**（这两处仍有 Flutter 门），直接用 `android/ui.sh` · `tap.sh`」「**不跑 `build.sh`**（构建交回主 agent）」
- [ ] 完成标准是否已写成断言（优先）或至少可机器判定；是否写明「不得仅用截图作证据」
- [ ] **是否写明起始页面状态**（登录页 / 已登录 / 首启协议页）以及**是否允许清数据**？未写清时子代理会自行 `adb shell pm clear`，复现前提漂移
- [ ] 等待页面就绪是否用 `android/settle.sh` 或 `adb shell sleep N`（裸 `sleep` 不在白名单，会被秒拒）
- [ ] 步骤是否**编号、具体、可执行**（而不是「测一下登录」这种模糊描述）
- [ ] 完成标准是否**可判定**（有明确日志关键字或页面元素，而非「看起来正常」）
- [ ] 若判据是日志签名：是否已在源码 `grep` 确认该字符串存在（防 `play() called` 这类凭空签名）
- [ ] 预估 >60s 的命令是否已标注走 `bg.sh`，且等待方式是**短轮询**而非单次长 `wait`
- [ ] 是否说明「日志无新增 ≠ 卡死」，避免 agent 因日志静止而提前放弃
- [ ] 关键定位失败时是否给了**降级路径**
- [ ] 重试阈值是否与 autoDebug 的「三级重试」一致（共 3 次执行 / 连续失败 2 次即停）

> 重试阈值务必与 autoDebug system 的「失败处理」小节保持一致：原命令重试 1 次 → 降级 1 次 → 停止回报。
> 两处数字冲突时模型会服从更近的任务 prompt，从而跳过降级、直接放弃——正是本模板要防的问题。

## 反例（会导致提前返回）

| 写法 | 问题 |
|---|---|
| 「跑一下登录流程」 | 无步骤、无完成标准，autoDebug 自行发挥 |
| 「构建然后安装」 | 未说装到哪台设备、用什么方式、判据是什么 |
| 「点登录按钮」 | 单步简单命令，派 autoDebug 反而更慢（应走 build 的「真机验证快捷通道」直接执行） |
